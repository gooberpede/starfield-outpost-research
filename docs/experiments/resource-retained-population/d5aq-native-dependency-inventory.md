## Indirect/forwarded owner branches retained

The inventory includes the following concrete aliases from D5AM's receiver
root, independently byte-authenticated again for D5AQ:

- Provider, point and area readers use ProcGen `+0x40`; methods `0x1407a50d0`
  and `0x1407a5210` also use it while separately owning `+0xd0`. Their three
  additional shared decrements are preserved.
- Source-map client `0x1409829b0` has inline final/recursive writer releases,
  distinct from the generic release helper.
- `0x1407a4b90 → 0x1407a4cc0 → 0x1407a38c0 → 0x1407a3b00` captures and forwards
  the actual owner. Callback table `0x144b3f1a8`, slot `+0x10`, invokes
  `0x1407b1410 → 0x1407b1bd0 → 0x1407a4730`; the larger captured context forwards
  element zero back into inspected recursion. It is not assumed to be a direct
  ProcGen receiver merely because it holds one.
- Creation functor table `0x144b3efe8` copies its captured word through
  `0x1407b0990`; invoke `0x1407b0980` jumps to `0x1407a6700`. Its actual body
  does not consume the captured ProcGen field; its locks use another singleton
  and returned cache. This is positive capture-use inspection.
- `0x14079e220 → 0x1407ac4d0`, and the captured-context path through
  `0x14079e6d0 → 0x14079e060`, use ProcGen `+0x130` exact-word mutex and `+0xf8`
  cache map. Primitive `0x140323460` operates on the supplied word. Those paths
  cannot be added to watched `+0x40` release accounting by offset-name analogy.
- Nearby manager `+0x24`, cache `+0x18/+0xb8`, nested object `+0x20` and other
  singleton `+0x30` users are excluded by their actual receiver loads and uses.
