## Original lock and destruction controls

The [isolated native host](../../../research/resource-retained-population/d5ar_native_controls.py)
executes authenticated original instructions at their preferred addresses only
inside its own disposable process. Receipt `native-shared08.json` passes five
bounded controls:

1. An uncontended original shared acquisition increments the owned reader word.
2. Same-thread exclusive recursion admits a reader while exclusive bits remain.
   Thus admission alone cannot certify a coherent complete snapshot.
3. A foreign exclusive fixture makes the original shared helper wait until the
   owned writer releases. Windows thread-ID and wait services use installed OS
   implementations; this does not execute an engine mutator.
4. The complete original ProcGen destructor and original pointer-map clear run
   with an active reader word of 1. The destructor clears the owned map and
   slot holder, decrements a retained holder from 2 references to 1, and reaches
   backing release while the reader word remains 1. Unrelated empty-cache
   clears are explicit RET stand-ins and backing release records without
   freeing Python storage. The destructor and main map-clear instructions are
   unchanged. This directly falsifies reader-only destruction protection in
   that bounded owned case.
5. Original opcode lookup and expression dispatch deliver eight native callback
   arguments and the binary32 scalar result to an owned stand-in. The generic
   parser boundary is an explicit stand-in, not a live console parse.

The first host failed before mapping because `WakeByAddressSingle` was not an
export of this installed Kernel32 DLL. The corrected host resolves that service
and `WaitOnAddress` from KernelBase. No snapshot or success receipt was written
by that failed run. The session tool return preserves the failure; a local
failure note distinguishes it from the later actual passing receipts. Receipts
02–03 preserve intermediate method versions rather than being overwritten.
The final method also tests the return-before-release predicate and writes an
exclusive failure receipt for future nonzero child exits.

These are actual instruction controls, not proof of console-call safety. The
finite 20-second subprocess failure bound applies only to the fixture; it is
not a proposed healthy-capture cutoff. All mappings disappear on host exit.

the manager-only lease remains disproved. The maintainer explicitly extended

The candidate installs five startup detours: ProcGen destructor `0x14079d910`,
whole point consumer `0x14079df70`, its holder callback `0x1407affb0`, whole area
consumer `0x1421e07d0`, and area holder callback `0x1421e0f50`. They replace 29

Startup refuses an already-present manager, non-sole-thread patch admission,

The native publication completion byte at `0x14621a2d0` must become 1 before

COMMAND_READY; this works whether AddTask queues or invokes inline and does not
assume task affinity. The service thread is created suspended only to register
its completion wait before it can exit, then immediately resumed; it is not an
engine thread. It must end before the operator loads a save or constructs an

## Lifecycle repair after independent review

Build19 is preserved as the reviewed five-hook checkpoint, not the current
integration candidate. Further review exposed a real current-binding gap:
constructor early publication and the caller's final publication can restore an
older manager after an intervening binding without a ProcGen destructor epoch.
The original unchanged `0x141881f3d..0x141881f5c` block and owned constructor
stand-in reproduce that counterexample in `publication03.json`; the whole-phase
model covers both constructor execution and the return-before-final-store gap.
The initialized native branch independently bypasses construction. This is a
model around actual publication instructions, not execution of the full native
initializer or a sampled CPU suspension after CALL return.

That intermediate repaired candidate had nine detours: the original five plus initializer
`0x141881660`, installer `0x140789ce0`, true-reset `0x140788e70` and outer manager
destructor `0x140788bc0`. Those whole phases enclose early/final publication,
body setters, late owner clearing, ProcGen free and singleton clearing. They
share the original lifetime hazard/epoch; the guard itself neither calls nor
suppresses an engine operation. Each adds an entry/exit hazard and epoch update
even when unarmed. Total replaced engine bytes are 49 and relays occupy 36 KiB.
No generator, scheduler, lock-admission, visited-key or request hook was added.
This extension is a candidate safety repair, not permission to deploy it.

Null owner plus sole thread is insufficient if Preload is already executing
inside a phase before its early publication. The new startup guard therefore
fully unwinds the current thread to RIP zero using its Windows stack limits and
runtime metadata. It excludes all 14 original parent/chained/FH4 action ranges
from `phase-unwind01.json`, including constructor and ProcGen teardown families.
The independently repeated receipt02 preserves the same ranges. The PE end of
the initializer is `0x141882b3d`, one byte beyond the earlier Ghidra half-open
approximation. Seventy-four action targets have no containing runtime entry;
they are not guessed to be leaves. Missing metadata, unreadable stack, malformed
entries, nonprogress or unwind exceptions refuse. There is no 62-frame absence
claim or arbitrary healthy stack-depth bound. Shared cleanup ranges can cause
conservative refusal. Stack status/frame count is recorded in startup receipts.
This guard precedes module pinning, avoiding permanent residency merely from a
stack-refusal path. It does not infer source semantics from a successful walk.

## Lifecycle admission repair: source-ending checkpoints superseded

Independent review reproduced ending final05/06 controls but rejected their

lifecycle admission barrier without adding patch sites.

A whole phase takes exclusive admission only long enough to wait for prior
copies, increment active-phase count and advance epoch. It releases the SRW mutex
**before original native code**. Its active count stays nonzero through the whole
original and completion advances epoch before dropping the count. Ordinary
same-thread nested phases count under their outer admission without recursively
acquiring SRW. Multiple mutators can overlap their originals; the observer does
not serialize native engine locks in opposite orders. The earlier proposed
whole-original exclusive lock was rejected because installer callers can already
hold a manager lock while reset obtains that lock later. Holding the observer
mutex across those originals could have introduced an engine/observer inversion.

The actual callback uses TryAcquireSRWLockShared, then checks that no phase is
active while holding shared ownership. It never waits for lifecycle admission
while it holds a native ProcGen reader. Active phase or contention produces

released leases refuse before the supplied reader is called. Source reads keep
the additional source-ending gate; lock order is lifecycle then source. Source
marking releases its gate before forwarding free and never waits for lifecycle
admission while source protection is held.

copy's shared scope before mutation. An already-admitted phase makes the callback
refuse promptly, so an original phase waiting for a native reader does not cause
the callback to wait for that phase. When no phase is active at admission, shared
ownership prevents the next one from admitting until the complete owned copy and
final binding checks finish. The mutex releases before original callback
continuation and normal publication. No native query, engine mutex acquisition,
alertable dispatch or IO occurs in the protected observer copy. Ordinary own

## Command admission and exact generation ownership

The final review challenged overlapping console handlers and a native area

[Microsoft's exclusive try-acquire](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-tryacquiresrwlockexclusive)

capture can be accessed. A contender returns zero and an owned debugger
diagnostic without waiting or calling the native console. The winner releases
in `finally`. This adds no permanent native patch or engine-reader lock.

The capture phase and command generation occupy one atomic word. Each eligible
scope records its generation at entry. Callback, no-callback cleanup and
operation completion must atomically claim that same generation's `Armed`
phase. A later command can begin only after the prior worker signals exit.
After a successful claim the exclusive owning path publishes the result and
the worker finishes it before the next command can mutate the buffer.

Owned mode 60 overlaps two registered handlers, checks that the rejected call
leaves all capture state unchanged, then completes the single admitted capture.
Mode 61 pauses one eligible callback, completes that command through another
operation, re-arms through the registered handler, resumes the older callback
and checks zero borrowed reads and no claim of the new command. A fresh
eligible operation completes the second command. The proposed pilot and series
retain one operator command per fresh process.
