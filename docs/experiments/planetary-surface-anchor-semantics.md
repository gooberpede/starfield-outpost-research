## Decisive native and definition chain

All addresses below are **preferred static VAs** in pinned Starfield.exe, image base `0x140000000`; subtract that base for RVA. No address is a live pointer or portable hook. Local exports retain original names and operand listings; explanatory aliases below do not rename the analysis project.

1. **`FUN_141686a00`, RVA `0x01686a00`: map selection to spherical angles.** Cursor unprojection through `142be3800`/`142be3900` supplies a ray. A ray/sphere intersection uses the body's displayed centre at input +0x60/+0x64/+0x68 and radius +0xc8. `1404a7da0` forms an inverse matrix; the centre-relative hit is transformed and normalized into body-oriented x,y,z. At `141686cb7–cf8`, float components become doubles; first `atan2` at `141686cdd` receives z and sqrt(x²+y²), second at `141686cef` receives y and x. Stores at `141686cf4/cf8` put **longitude then latitude** in two consecutive doubles. The horizontal norm is rounded to float before sqrt, then widened: the analytical equation below is not a bit-exact emulator of those float stages. Decompiler intrinsics/prototypes alone were not used to resolve this.
2. **`141686000 → 1416874f0 → 1416885d0`: selected-site state.** The first calls the selector at `1416866bb`, then processes its pair. `1416874f0` initially copies the pair; one terrain/feature branch can replace it using `142332410` with indexed terrain coordinates. Thus a selected-site anchor can be adjusted/snapped; the cursor point is not automatically the final persisted anchor. `1416885d0` copies the selected pair into state +0x12a8/+0x12b0 and calls `142104ff0`. The full downstream travel/creation chain is not closed here.
3. **`140ad0650 → 140ad55b0` and `140779300 → 140771ac0`: overlay creation/registration.** `140ad0650` consumes the input pair in overlay construction and naming, copies it unchanged with the created object's ID at tuple +0x10, and calls `140779300`. `140ad55b0` formats the **second** component as `Lat` and **first** as `Lon`; this is an independent semantic naming consumer, not the generic UI geolocation string. `140779300` supplies body/planet identity and the tuple to `140771ac0`. That function compares existing entries' double +0x20/+0x28 and world ID +0x30, then queues a `CTPlanetOverlayData` command containing the two doubles, ID and edge key with type key `1461e1d9c`. Callback `1407772c0 → 140774ee0 → 140777560` inserts/copies the tuple into the component store. Operand checks at `140777614–637` compare both doubles and ID; `140777743–753` copies the tuple. These establish data association, not safe invocation or transaction/load authority.
4. **`14231d000`, `1423204d0`: component identity.** Registration associates key `1461e1d9c` with `PlanetWorldSpaceData`; factory/type RTTI names `BSGalaxy::CTPlanetOverlayData`. This links the creation path to the planetary overlay store. Type registration is not itself a proof of its generic serializer's wire order.
5. **`14076ec00`: PNDT fixed-world definition loader.** The **pre-BDST CNAM branch**, tag `0x4d414e43`, reads records with **20-byte stride**: disk first double, disk second double, world ID. It swaps the two doubles into the longitude-first tuple and passes it to `140773090`, which queues `CTPlanetOverlayData`. The later CNAM inside BDST is a different one-byte body-type field. Last-field-only ESM catalogs silently lose this distinction; the new optional repeated-field reader preserves it. The loader's instruction export is capped, but its `full:` decompilation is complete; selected call/stride/order conclusions also have independent byte-level fixed-record matches. No claim of a complete PNDT parser follows.

## Representation and numerical challenges

Read the sampled pair as little-endian IEEE-754 binary64 `(lambda, phi)`. In the body-oriented frame exposed by the selector:

```text
lambda = atan2(y, x)
phi    = atan2(z, sqrt(x*x + y*y))
u      = (cos(phi)*cos(lambda), cos(phi)*sin(lambda), sin(phi))
longitude_degrees = lambda * 180 / pi
latitude_degrees  = phi    * 180 / pi
```

`u` is a unit direction, not a metric terrain position; no body radius, elevation or planetographic ellipsoid correction is supplied. Longitude may be displayed in [-180,180] or wrapped by adding/subtracting 360; at the seam +180/-180 are equivalent. atan2 supplies a principal signed longitude and latitude within [-90,90]; the stored samples do not prove the writer always canonicalizes every alternate representation. At a pole longitude is geometrically undefined. Here “positive latitude” means toward engine +Z; labelling it north is a stated convention only, pending compass/pole calibration. Positive longitude is the +X-to-+Y sense about +Z. Neither a geographic landmark nor texture seam defines zero in this investigation: **the matrix's +X does**. Absolute orientation in orbital appearance or resource maps needs another mapping.

## Bridge to the beacon and concrete remaining gaps

The established saved chain remains ordinary beacon → tagged parent/overlay → body-associated anchor. S1's case-5 local tuple is `(122.6921157836914,277.25439453125,18.35177230834961)`, not `(lambda,phi)` and not a body-centred vector. A0/A0C were freshly hash-checked, matching earlier SOR-EV-0004 identities and identical player XYZ `(120.827057,270.736237,17.5202465)`. Their Euclidean distance to S1's local candidate remains 6.830539 in **unassigned units**, with earlier-session/non-atomic conditions. These observations do not supply local origin, tile basis, scale or planetary radius; adding them to angles would be dimensionally unjustified.

**Unresolved C:** exact beacon longitude/latitude, tile-centre versus landing reference versus another overlay anchor within the site's frame, local compass axes/handedness, metric conversion and authoritative restoration. The site role is STRONG because creation couples coordinates to a generated world ID and fixed-city definition, while local beacon state is separate. It is not a claim that the anchor is physically at the beacon, ship or tile centre. Other beacons/objects in the same overlay could share the same planetary anchor regardless of local displacement; that is a prediction, not tested here.

**Specific missing mechanism:** the map pair can be resampled through the terrain index/cube-face conversion in `1416874f0 → 142332410`, and overlay construction uses `1407b6360`/`140ad01d0`/`140ad0400`. The relation between that body's terrain-face origin/basis/scale, generated world placement and a saved reference's local XYZ has not been reconstructed. Native exports expose promising operations rather than an inaccessible black box; this bounded pass does not assert offline exhaustion. Generic component wire serialization also remains incomplete, so no full decoder/save-edit guarantee follows.
