# Definition extension and persistence boundaries

[Answer](report.md), [catalogue](catalogue.md), [eligibility](eligibility.md),
[UI](ui.md). These are installed relationships and conditional predictions for
additional definitions. No plugin, mod, importer or supported API is implemented.

| Kind | Minimum evidenced relationship / boundary |
|---|---|
| Definition-driven discovery | Loaded non-deleted COBJ; nonempty FNAM list whose first keyword is in the configured WorkshopAllCategoryList; usable CNAM target. Adding only BNAM or a recognizable editor ID is insufficient. |
| Definition-driven grouping | Direct target for an ordinary distinct entry; target FLST plus `04000000` owning-recipe flag to preserve one group; ordered direct forms/child COBJ entries produce prospective variants. Unset flag descends into separate nodes. Native form-type/buildability predicates still apply. |
| Conditions/costs | Actual recipe/list-entry condition context, operand identities, FVPA requirements and typed perk/research descriptors. JNAM supplies a shared quota identity, independently of menu category. All gates remain subject to ordinary budget/placement/admission. |
| Assets | Form name/description, model/PackIn construction data and suitable thumbnails; native plugin-aware `CL.dds` image identity. Resource/power operational descriptions need the actual corresponding definitions/properties. New arbitrary fields or category art are not guaranteed by a new recipe. |
| Script-assisted | Existing progression/quest/global/AV changes can alter inputs to native evaluators. This does not supply a demonstrated script API to insert grid rows, safely invoke native routines, define a new UI field or force immediate coherent refresh. |
| Native/compiled-interface-dependent | Category specialization, condition retry policy, descriptor serialization, callback dispatch, placement validation, card sections/icon interpretation and cache/update epochs. A generic new category does not automatically inherit specialized harvester/builder behavior keyed by default-object equality. |
| Unknown/unvalidated | Arbitrary third-party plugin execution, winning override conflicts, runtime load-order changes, malformed/cyclic lists, every custom asset namespace, practical large-menu performance and safe native invocation. |

`140f4d630` walks **loaded** recipe records, rather than hardcoding a main-file
recipe ID list. Root/category resolution and current loaded form identities
therefore determine registration. SD2's installed SFBGS00D Shared Outpost Storage
is a concrete add-on construction using the ordinary Storage category and native
provider/admission path. This supports addition through existing relationships;
it does not certify an untested custom plugin or automatic asset compatibility.
The BM2 physical census deliberately does not merge winning overrides. Changing
record/list definitions can change the next rebuild's inputs, but a guaranteed
mid-menu dynamic reload/repopulation API is not established.

Category names/order and recipes/lists are definition-driven in the mapped
providers. Generic categories can supply ordinary entries through the common
route; behavior requiring a special UI layout, new command, new condition opcode
or a new operational interpretation would depend on existing native/compiled
support or separately implemented changes. Neither 204 sample roots nor u32
counter width establishes a maximum supported custom catalogue size.

## What persists and what is rebuilt

| State | Class | Evidence and limit |
|---|---|---|
| Menu root/category/recipe/list definitions | DEFINITION-DERIVED | Loaded records and default-object bindings feed `140f4d630`; actual override winners are not reconstructed here. |
| Native node maps and grid/variant arrays | RECONSTRUCTED / TRANSIENT | Explicit map clearing, allocation and rebuild; UI provider owns begin/end/capacity vectors and selection IDs. No need for a hypothetical serialized menu catalogue record. This is a positive lifecycle trace, not an exhaustive search of every save channel. |
| Current prospective selection | TRANSIENT in the mapped menu model | Node/leaf/index callbacks set current state; no new persistent selection guarantee claimed. |
| Player perks/research/quests/globals | MIXED persisted progression and loaded/effective state | SD2/L1/E1 progression paths; operands are reevaluated in player/Workshop context. A historical saved value is not current post-load authority. |
| Selected Workshop members/quota/budget | MIXED | Saved/default references and owner relations reconstruct representative membership; L2 usage AV persists while summary/UI reconstruct. Existing over-limit objects are not automatically evicted by a new-build admission check. |
| Placed construction and BM1 variants | PERSISTED identities/relations plus reconstruction | Workshop root/member/owner records and BM1 selected PKIN/anchor links; preconstruction furniture variants do not imply the same placed-object replacement mechanism. |
| Producer configuration and schedule | MIXED | E2/E3 persist resource AV selection and producer rows; effective interval, current eligibility and delivered output remain separate. Menu candidate membership is not a producer registration. |

Prior mature-save evidence is used only for these relevant positive contracts:
BM1's HIST-0210 anchor/replacement joins, SD2's positive shared-storage membership,
and E2/E3's saved selected producer rows. No fresh BM2 save scan, catalogue-save
record, full outpost membership claim, loaded UI total or reload experiment is
invented. Ship/house definitions share some category vocabulary and have explicit
context predicates; terrestrial discovery does not qualify full ship construction,
ship saving or arbitrary external integration.
