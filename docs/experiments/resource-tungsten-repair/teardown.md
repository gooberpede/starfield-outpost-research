# STOP and thread-exit repair

The original D4A stream ends with transfer 3027, positive ACK 3027, THREAD_END lifetime 2, then LOSS containing `phase context win32=31`. Stderr names that failed context operation; controller exit 2 and wrapper exit 1 are observed. No EXIT_PROCESS or spontaneous exception is in that receipt. Target exit code and exact failing thread are UNKNOWN. The [accepted Phase B report](../resource-tungsten-acquisition/phase-b.md) remains unchanged.

Source inspection gives the causal control-flow defect: transfer sampling retires the updater stack; ACK STOP requests termination and skips the ordinary rearm; a subsequent EXIT_THREAD erases its thread and unconditionally calls phase rearm. With no active updater, it changes consumer mode to generation mode and reads/arms every remaining thread. Terminating threads may no longer satisfy those observation obligations. The precise historical API timing is inferred, while the failed API site/return and unsafe path are separately established.

The original build08 synthetic controller was run with the new pinned fixture, first with three, then 96 waiting native worker threads. Both legacy trials returned zero because their late context operations succeeded. They **did not reproduce `win32=31`** and their strict historical-error expectations failed; legacy-terminal01/02 preserve those failures. Both did reproduce post-ACK PHASE/rearming. Legacy-terminal04 tests that actual unsafe operation explicitly. This is an engineering counterexample to the no-late-rearm invariant, not a manufactured Windows error or a claim of exact historical timing replication.

## Correction

[Controller source](../../../research/resource-tungsten-acquisition/controller.cpp) now commits monotonic terminal intent before termination, including refused/missing ACK and operator STOP. The common rearm entry refuses work after that commitment. Terminal debug events drain without sample creation, initial thread arming, phase/context reads or resume verification. Known owned execution traps are continued; other exceptions retain NOT_HANDLED disposition. Thread exits remove bookkeeping; late thread creation creates no observation obligation. There is no detach or restoration onto dying threads.

Each WaitForDebugEvent result has one explicit pending-event owner. Ownership clears only after successful ContinueDebugEvent. Fatal recovery terminates at most once successfully, continues the still-owned event, then drains to EXIT_PROCESS. Invalid-handle termination and invalid-owner continuation probes fail loudly with controller exit 2; cleanup uses the real retained handle/event and preserves evidence. The ten-second failure-drain limit bounds engineering recovery after disposal; it is not an operator-response or scientific-capture deadline. A drain timeout is reported, not converted into success.

The normal path records actual target exit code and whether STOP was requested before the exit. Fixture event handles and independently opened process handles are closed once on each return path; debug-event process/thread handles retain Windows event-lifetime ownership. No event is synthetically redelivered. Duplicate continuation is tested by a second actual ContinueDebugEvent call, which Windows refuses; the controller does not consume a different event to disguise that error.

## Real Windows tests

Local terminal04 contains twelve cases. STOP with three and 96 waiting threads drains actual EXIT_THREAD events before EXIT_PROCESS, with no post-STOP PHASE, SAMPLE, THREAD_BEGIN, STARTUP_ARMED or RESUME_VERIFIED. The pending-stop fixture synchronizes STOP while a genuine worker EXIT_THREAD event is outstanding. Startup helper-thread exits cover the before-STOP case. A terminal exit arrives where legacy code would attempt phase readback; repaired code makes no such read.

Crash-before and crash-after retain actual exception and process-exit codes, separately from controller status. No-hit exits normally with code zero. Refused, partial and EOF ACK cases stop after one persisted sample without useful science. Termination/continuation failure probes use real invalid API arguments, not simulated successful calls. All synthetic PIDs are checked absent after completion, and all persisted receipts are reopened and independently decoded after success or failure. The Python harness returns zero only when expected outcomes and durable receipts agree; each intentional controller failure remains recorded as exit 2.

Limits: Windows does not ordinarily deliver duplicate debug events, so the duplicate test exercises actual duplicate continuation refusal rather than inventing a duplicate kernel event. Exact historical `win32=31` timing and future retail behavior remain untested. The demonstrated repair removes the observed unsafe operation and qualifies terminal drainage on real Windows targets; no new Starfield test is authorized or required.
