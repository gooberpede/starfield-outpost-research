# CODEX BRIEF — SOR RG2-D5T
## Feynman V Outpost 2 Variant Enumeration and Visual Mapping

### Authority and intent
This brief authorizes the next offline research step after D5S. Its purpose is to keep **Feynman V outpost 2 / second Feynman V source** under focused investigation and to answer, as completely as the authorized methods permit, **how many distinct ordinary generation outcomes exist in the pinned scope, what determines each outcome, and how those outcomes differ visually**.

This brief is governed by the current project research-completion rules. The **controlling scientific question** must remain authoritative throughout the task. Discovery of an additional dependency is **not** a reason to close the investigation while an authorized avenue remains open.

### Controlling scientific question
Within the pinned normal-generation scope already established for the second Feynman V source, **what distinct ordinary resource-generation outcomes are actually possible, which admissible winning queries produce them, and how can those outcomes be rendered as accurate, reviewable maps?**

### Scope and target
Primary target:
- **Second Feynman V source / Feynman V outpost 2**
- Analytical source identity already established in prior D5 work
- Pinned executable/data baseline inherited from D5S unless explicitly reverified to a different identical baseline

Primary domain:
- **Ordinary resource generation** within the D5S normal-arrival / fixed-input contract
- Query-winner variability and resulting surviving geometry
- Visual mapping of the resulting deposits

Out of scope unless required by a demonstrated dependency:
- Generalization to all planets or all sources
- New SFSE/plugin development
- Retail/game launch or live observation
- Save mutation or speculative save-file archaeology
- Publication or external disclosure

### Scientific objectives
Codex must answer the following questions.

#### Q1 — Variant census
How many **distinct ordinary generation outcomes** exist for the pinned Feynman V outpost 2 target, within the defined normal-generation scope?

“Outcome” here means a materially distinct surviving ordinary geometry result, not merely a different intermediate request or a different internal weight vector.

#### Q2 — Determining inputs
For each distinct outcome identified in Q1, which admissible winning queries and effective native inputs produce it?

This must include, where relevant:
- winner/original query coordinates
- converted/query-space coordinates if distinct
- sampled ordinary mask value
- effective ordinary resource weights
- other effective inputs necessary to distinguish outcomes

#### Q3 — Equivalence classes
Do multiple admissible winning queries collapse to the same geometry outcome? If so, identify the equivalence classes. If not, establish the evidence for distinctness.

This question exists to prevent premature closure after identifying only two winners or two mask values.

#### Q4 — Visual mapping
Produce durable visual maps of each distinct outcome, plus a comparison view, so that a human reviewer can see the actual spatial differences without interpreting raw receipts or tables.

### Method expectations
Codex must follow all material authorized dependencies needed to answer Q1–Q4. In particular:
- If additional qualified candidate winners must be enumerated, do so.
- If same-mask queries must be compared to establish equivalence or non-equivalence, do so.
- If full first-resource geometry execution is insufficient to classify an outcome, pursue the minimum further ordinary-generation work necessary to discriminate it.
- If an indispensable input cannot be recovered from the executable and static game data, then and only then perform a narrowly targeted, read-only save investigation consistent with the project protocol.

Codex must not stop with “two variants demonstrated” unless it has also shown either:
1. those are the only distinct outcomes in the pinned scope, or
2. a specific, evidenced blocker prevents further classification.

### Visualization requirements
Visual outputs are **mandatory deliverables**, not optional supplements.

#### V1 — Canonical frame
All maps for this task must use a **single canonical frame** so they can be compared directly.

Unless a better justified frame is required by the underlying data, use a common layout broadly similar to the example SVGs already provided by the maintainer:
- stable orientation
- stable origin and extents
- stable scale
- stable title/legend placement where practical
- vector format preferred

The examples are precedents for usability and framing, not a requirement to copy their appearance exactly.

#### V2 — Geometry fidelity
Where the data allows, show the **actual generated deposit shapes** (“blobbiness”), not only bounding boxes.

Order of preference:
1. exact generated/retained region geometry
2. exact reconstructed geometry faithful to the native result
3. only if unavoidable, a clearly labeled approximation

If approximation is unavoidable for any layer, Codex must identify exactly what is approximated and why.

#### V3 — Color provenance
Use resource fill/stroke colors recovered from the relevant records (including IRES or directly associated data) if that provenance can be established. If not, use a documented fallback palette and state the fallback clearly.

Color assignment must be:
- stable across all variants
- visually distinct between resources
- traceable to a documented source or fallback rule

#### V4 — Required visual deliverables
At minimum, produce:
1. **One SVG map per distinct outcome**.
2. **One comparison SVG** showing the distinct outcomes side-by-side and/or as an overlay/difference view.
3. Optional convenience PNG exports if useful, but SVG remains the durable required format.

#### V5 — Required machine-readable geometry outputs
Produce machine-readable geometry exports sufficient to support the visualizations and review. Acceptable formats include JSON/CSV and, if useful, GeoJSON-like structures. The chosen format must be documented and reproducible.

At minimum, each outcome export must identify:
- outcome identifier
- resource identifier/name
- query winner / equivalence-class identifier
- coordinate basis
- geometry primitives used for plotting
- any clipping or transformation applied

### Completion contract
The permitted terminal dispositions are **COMPLETE**, **INCOMPLETE**, or **BLOCKED**, as defined by the project governance rules.

#### COMPLETE
COMPLETE is allowed only if Codex has either:
- exhaustively classified the distinct ordinary outcomes in the pinned scope, including the mapping from admissible winner(s) to outcome(s), **or**
- completed a bounded negative result whose scope fully answers the controlling question in the authorized domain.

A COMPLETE result must include the mandatory visual deliverables.

#### INCOMPLETE
INCOMPLETE applies if distinct authorized investigative avenues remain and the controlling question is not yet answered. Good documentation does not change this.

#### BLOCKED
BLOCKED is allowed only if Codex demonstrates a specific indispensable obstacle, the alternatives examined, why authorized methods cannot bypass it, and the minimal additional capability or authorization required.

“Codex could not find more variants” is **not** a blocker.

### Acceptance criteria

#### D5T-AC1 — Authority, pins and protections
Reverify the exact baseline and protections; remain offline and read-only. No game launch, plugin deployment, save mutation, publication activity, staging, commit or push.

#### D5T-AC2 — Controlling question and active ledger
Freeze the controlling question, Q1–Q4, intended scope, success/falsification conditions and parent linkage before substantive work. Maintain the investigation ledger throughout and preserve discarded hypotheses and failed approaches.

#### D5T-AC3 — Candidate-winner census
Enumerate the admissible candidate winners far enough to support a defensible outcome census. Show which candidates are genuinely feasible, which are excluded, and why.

#### D5T-AC4 — Outcome discrimination
Demonstrate whether candidate winners collapse to identical outcomes or produce distinct ones. Do not rely on mask or weight differences alone where a geometry comparison is required.

#### D5T-AC5 — Distinct-outcome classification
Produce a defensible classification of the distinct ordinary geometry outcomes for the target in scope. If the set is partial, disposition cannot be COMPLETE unless a bounded negative result fully answers the authorized question.

#### D5T-AC6 — Determining-input explanation
For each distinct outcome, identify the winner/query/effective-input conditions that produce it, including mask value and any other effective discriminators required by the evidence.

#### D5T-AC7 — Visual mapping quality
Produce the required SVG maps and machine-readable geometry exports in a canonical frame. Visuals must be traceable to the research geometry and must portray deposit shape fidelity as far as the evidence allows.

#### D5T-AC8 — Color provenance and presentation clarity
Document the provenance or fallback rule for resource colors. Ensure maps are legible and directly comparable without requiring the reader to decode raw receipts.

#### D5T-AC9 — Conditional save gate
Perform read-only save investigation only if an indispensable input is demonstrated missing from executable/static data. Document the trigger if invoked, or the non-trigger if not.

#### D5T-AC10 — Independent completeness review
The scientific/completeness reviewer must challenge whether the outcome census is actually complete within scope and identify the highest-value remaining avenue if not. A technically correct but prematurely closed investigation must be returned as REWORK/INCOMPLETE.

#### D5T-AC11 — Durable delivery and exact review
Provide the report, variant catalogue, geometry exports, SVGs, source ledger, review record and exact delivery manifest. Verify complete/task-only diffs, hashes, editorial quality and repository cleanliness.

### Specific cautions
- Do not silently narrow the task from “distinct outcomes” to “distinct masks” or “distinct winners”.
- Do not substitute bounding rectangles for deposit shapes unless no better geometry is available and the limitation is explicitly labeled.
- Do not treat two winners as exhaustive merely because two have been demonstrated.
- Do not infer retail frequency from offline feasibility.
- Do not conflate “different native inputs” with “different surviving geometry” unless the geometry difference is actually demonstrated.

### Expected next-step value
A successful D5T result should tell the maintainer, in a form that is both scientifically defensible and visually intelligible:
- how many ordinary generation outcomes are currently supported for Feynman V outpost 2,
- what determines each outcome,
- whether the practical variability appears binary or more complex,
- and what those alternative deposit maps actually look like.
