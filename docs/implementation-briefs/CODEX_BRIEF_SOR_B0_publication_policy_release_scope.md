## 2. Settled publication policy — record faithfully

### A. What is and is not distributable

- **Candidate:** original project-authored research explanations, algorithm descriptions, diagrams, native addresses/offsets, carefully bounded illustrative assembly or pseudocode snippets inside research documents, and original project-authored scripts, helpers and build definitions that contribute to reproducibility. Carefully distinguish original analysis from redistribution of copyrighted or decompiled material. Assess actual snippets against rights policy; the presence of assembly/pseudocode in a document is not itself a wholesale prohibition.
- **Exclude:** standalone decompiled `.c` / `.asm` files, wholesale decompiler output or bulk disassembly, Ghidra databases, installed Ghidra/xEdit/x64dbg and their installations, game executables, libraries, ESM/BA2 archives, game-install INI files, and files from the `Starfield/` installation. These remain **outside** the project and public release. Original project-authored source code is not game decompilation merely because it analyzes game data.
- **xEdit scripts:** candidates if authored by the project and needed for reproducibility; include only if not already tracked. Installed identical copies are not new publication content.
- **Game-derived dumps:** normally exclude outputs copied/extracted from ESM or BA2, except for individually evaluated essential, nonsensitive evidence that passes rights review. Favor documenting extraction methods that operate on a reader's own installed game.
- **Third-party saves:** exclude absent specific redistribution permission. **First-party control saves and screenshots:** legitimate publication candidates, not presumptive blockers. Do practical privacy/provenance checks; character names are acceptable and are not presumed identifying. **First-party mature saves:** higher scrutiny and inclusion only where essential or unusually valuable. Do not assert a categorical Bethesda prohibition where no such specific rule has been established, but do not represent customary community distribution as an express redistribution grant.
- **Evidence formats:** preserve source-file bytes and original hashes, package chosen binary evidence as compressed supplementary archives with archive manifests, per-file SHA-256, experiment references, and clear provenance. Avoid permanent bulk binaries in ordinary Git history by default. Do not use third-party file-sharing hosts; proposed archives must be reachable from the project's GitHub repository/release.
- **Licensing:** GPL-3.0-or-later for original project-authored work, consistent with the intent already recorded in `LICENSING.md`. The grant does not purport to license Bethesda's underlying game material, third-party saves, proprietary tools or external dependencies. Track author/copyright and any applicable third-party notices/permissions separately, including existing SFSE header licensing boundaries.

### B. Version-specific research baselines and future game updates

- **A research release identifies its applicable game baseline.** Record the exact pinned `Starfield.exe` version/build and hash for the primary accepted baseline (currently predominantly retail `1.16.244.0`, subject to verification of the governing pins), plus relevant installed ESM, BA2/interface, script and configuration baselines where they materially support claims. A released snapshot must disclose **historical experiments using other versions** and per-finding coverage rather than retroactively assign all findings to the headline build. Never publish proprietary source inputs merely to communicate their hashes.
- **Stable research identity is separate from address.** Plan for a durable, version-independent identity for each *significant* native function/structure/definition/interface, joined to version-scoped executable addresses, object offsets, FormIDs or other locators, pin evidence and semantic coverage. Existing historical function registers and source pins should be reused; B0 must **design a maintenance policy, not implement or populate a complete new crosswalk**. Avoid imposing identifiers for every incidental function or duplicating existing registers. Source addresses, bit offsets, and signatures in historical reports remain version-bound evidence; never silently rewrite them to new-build values.
- **Changes are not assumed from movement or stability of addresses.** A relocated function can preserve behaviour; an unchanged address can host modified behaviour. Future assessment should compare game definitions, Papyrus/compiled UI, relevant settings, native call/data paths and original regression witnesses according to actual changes. It must recognize split, merged or removed native functions rather than forcing one-to-one mappings.
- **Incremental requalification, not automatic comprehensive rediscovery.** For a later game build, first inventory and hash changed inputs, compare definitions and exposed interfaces, relocate only significant native locators necessary to reassess the selected findings, and run proportionate targeted verification. Label results independently as `REVALIDATED`, `CHANGED`, `CARRIED FORWARD — NOT REVALIDATED`, or `UNRESOLVED`, with precise evidence, applicable versions, and limitations. A new-build locator match alone is not behavioural revalidation. Unchanged definition bytes alone do not prove every runtime consumer unchanged.
- **Release decision and cadence.** A Bethesda update prompts assessment, not an automatic new release. A subsequent tagged research release follows only after an independently reviewed update-qualification record and maintainer approval. Record the validated/changed/carried-forward coverage explicitly. Older tagged releases and their historical coordinates and offsets remain intact. This is maintenance of a research archive, not a version-independent compatibility promise or software distribution.
- **B0 authority boundary:** document a prospective baseline manifest schema, register/crosswalk approach, requalification statuses and version-update workflow. Do not run a new-build investigation, scan or reimport executables, produce native crosswalk data, run regressions on new software, change historical offsets, or produce a tagged release under B0.

### B. Source versus products of source

Preference: **publish original helper source and required build/run instructions over packaged executables or generated dumps**, where doing so materially enables reproduction. Evaluate method by method. Distinguish maintained source, scientifically significant archived source at the historical revision, disposable helpers, generated output, protected original evidence and external prerequisites. Old source hashes that no longer match current files are a source-identity problem: do not silently relabel present code as the historical version. B3 should produce exact source-version and reproducibility decisions using RR1-010/021, without indiscriminate promotion of the ~15,008 ignored source/config candidate occurrences.

### C. Privacy and historical fidelity

Practical inspection should look for account names/IDs, Steam or service identifiers, Windows user details, personal paths/metadata, credentials and accidental private material in candidate saves, screenshots, derived exports and current/history Git content. Character names alone are allowed by maintainer decision. Keep evidence originals untouched and their hashes intact. Where privacy or rights concerns arise, exclude the item or propose a clearly identified derivative for *later authorization*; B0 must not modify a protected original.

Historical absolute paths, missing external evidence and superseded statements may legitimately remain in dated archives, but current instructions and public navigation must not depend silently on inaccessible local locations. Published material must not contain broken relative references masquerading as accessible evidence.
