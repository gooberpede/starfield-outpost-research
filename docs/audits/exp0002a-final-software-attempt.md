## Backend and exact mechanism

Existing Microsoft CDB/dbgeng10.0.19041.5609, using local-only symbol paths, `-pd` (detach rather than kill on debugger exit), and explicit PID attachment after the operator is UI-paused. Exactly one `bp0 /1 <fresh-base+0x0183c590> "command-file"`: native one-shot software INT3, process-wide site, no per-thread DR0/DR7 writes. The attached process initially stops at the engine's standard attach break-in; that and a possible deadline control break are debugger control operations, not additional research sites. `bl` must show no pre-existing research breakpoints and then exactly the one intended site. No exception suppression, stepping/rearming loop or game invocation.

Ghidra 12.1.2's installed `local-dbgeng-attach.py` requires a Ghidra Trace RMI connection, attaches via its Python agent, waits and enters a REPL. `ghidradbg/methods.py` delegates software breakpoints to dbgeng through `dbg().bp`. That bridge has no established ready/flush/deadline integration for this capture. Direct CDB provides the same installed Microsoft engine's native one-shot breakpoint and durable command output without introducing/qualifying that additional integration. This selection is based on the minimal needed operation, explicit one-shot semantics and evidence transport, not a claim that Ghidra or dbgeng cannot work. No new third-party or maintainer implementation was incorporated.

Microsoft reference consulted 2026-10-07: [bp /1](https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/bp--bu--bm--set-breakpoint-) deletes the breakpoint after its first trigger; [qd](https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/qd--quit-and-detach-) detaches and leaves the target running. [CDB session ending](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/ending-a-debugging-session-in-cdb) documents `-pd`. Separate installed tools/documentation only, SOR-S-0117/0123 extension; no copied example implementation.
