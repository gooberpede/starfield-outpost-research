## Operator handoff and clocks

**Review hold now.** After later approval: user launches normally through Steam without SFSE, loads disposable Save3-based state, opens Pause > Save, highlights New Save, does not confirm, reports ready. Only then attach/configure. Parent/backup integrity and loaded-module absence/build/process checks are fresh. No game launch/deploy is delegated to the capture tool.

1. SETUP: allow up to 300 seconds as a separate operational watchdog, with operator progress updates. The menu is paused by the game, but its threads are not necessarily suspended and the debugger may report running. Do not wait five seconds for a particular attach-paused notification and declare failure. Use a supported, explicitly owned debugger stop or balanced thread suspension only when required to inspect/configure hardware registers; record it. Do not treat the game's UI pause as proof GetThreadContext is safe without such control.
2. ARMED_WAIT_CONFIRM: only after PID/build/hash/base, exact bytes, owned hardware state on all relevant threads, no unintended breakpoint, evidence sink and cleanup readiness are verified. Release setup-only stop/suspension so the save UI can respond, while keeping it menu-paused. Persist and report ARMED. An independent 120-second operator-coordination watchdog may disarm on no confirmation; it is not the scientific ten-second window and produces NO_ACTION, not a failed save-path result.
3. CAPTURE: starts only after ARMED **and the user's actual New Save confirmation**; one request or 10 seconds, then retire. Attach/configuration and waiting for the user consume none of this budget. No automatic UI click. Actual click time may not be visible to the debugger: retain the user's confirmation report with receipt time and first REQUEST_ENTRY time as separate anchors. The first entry is the earliest engine-side candidate evidence after the click, not proof of its cause. Do not substitute ARMED time or pretend chat receipt is exact click time. The future adapter must accept an early entry while confirmation reporting is in transit as a provisional pending record, then correlate with the operator report; an entry known to precede confirmation is an anomaly, not a manual save. For zero hits, the receipt of the operator's after-click confirmation starts the 10-second no-hit deadline; report the unknown click-to-receipt gap explicitly. The 120-second coordination bound limits that gap without redefining it as science time.
4. AFTER CAPTURE: persist first, retire only owned state, detach, verify debug registers/code and balanced suspensions; inspect delayed health and ask for UI response. No forced termination or automatic retry. Normal exit/sync and copy-first verified archive remain separate; no live deletion. One entry never proves completion/durability/cloud bookkeeping, so Stage C remains blocked until later evidence closes those questions.

The next adapter must retain explicit setup_started, armed, operator_confirm_received, first_hit, capture_started/anchor_kind, capture_finished and cleanup_finished timestamps. A hit/confirmation race or absent confirmation remains distinguishable from a reliable one-request capture. This correction provides the exact design and machine-readable limits, not an untested promise of live timing enforcement.
